# Aatish FM — Complete Frontend Visual & Interaction Specification

## 1. Purpose

Build a single-page **Vite + React** frontend for a private romantic radio experience.

The supplied reference image is the primary visual reference. The implementation should recreate its visual language using **React, CSS, SVG/icon libraries, animations, and browser APIs**, rather than turning the entire design into one static image.

The frontend must remain fully interactive and backend-ready.

The key principle is:

> The screenshot is a design reference, not a background image.

The default interface should require almost no static image assets.

---

# 2. Core Visual Philosophy

The experience should feel:

- romantic
- intimate
- premium
- cinematic
- minimal
- elegant
- slightly nostalgic
- calm
- personal

It should feel like:

> "This is a private radio station made just for you."

It should **not** feel like:

- Spotify
- a generic music player
- a dashboard
- a streaming-service clone
- an animation showcase

Use visual restraint.

The design should rely on:

- negative space
- typography
- subtle gradients
- glass/translucent surfaces
- thin borders
- warm highlights
- soft glow
- controlled motion

Avoid excessive decoration.

---

# 3. Static Assets vs Generated UI

## 3.1 Default requirement

The UI should be approximately **95% generated through HTML/React/CSS/SVG**.

Do not create the complete interface as a single PNG/JPG.

The following should NOT be static images:

- central radio card
- borders
- background glow
- frequency text
- radio icons
- heart
- divider lines
- dynamic display text
- waveform
- arrows
- play/pause button
- button glow
- decorative sparkles
- horizontal lines
- station selector
- dropdown
- animation effects

All of these should be generated by the frontend.

---

# 4. Static Assets That May Be Used

Only a small number of static assets may be useful.

## 4.1 Custom background image — optional

Support an optional custom background image.

Example conceptual asset:

```text
public/images/custom-background.jpg
```

This is optional and should NOT be required for the default design.

If a custom background is supplied:

- preserve the UI readability
- apply a dark translucent overlay
- avoid allowing the image to overpower the radio interface
- retain the same burgundy/cinematic atmosphere

The background should be configurable rather than hardcoded into the component.

Possible conceptual configuration:

```text
backgroundImage
backgroundOverlayOpacity
```

---

## 4.2 Optional noise/film texture

A very subtle noise or film-grain texture may be used if the visual result benefits from it.

If used:

- it must be extremely low opacity
- it must never distract from text
- it should not look like a visible pattern
- it should be decorative only

A tiny PNG/WebP texture is acceptable.

This is optional.

---

## 4.3 Audio assets

Demo audio files may be included for development.

Example:

```text
public/audio/demo.mp3
public/audio/demo-2.mp3
```

These are functional media assets, not visual assets.

The production implementation should ultimately consume audio URLs supplied by the backend.

# 5. Background Specification

The default background should be generated completely using CSS.

## 5.1 Base colors

Use a dark burgundy/wine palette.

Suggested range:

- almost-black burgundy
- deep wine
- dark red
- muted rose
- subtle coral

Approximate conceptual colors:

```text
#160609
#25090D
#3A1117
```

Do not make the page bright red.

---

## 5.2 Background construction

Use layered CSS gradients.

The background should contain:

- dark base
- very subtle central radial warmth
- extremely subtle secondary glow
- darker edges

The center can be slightly warmer than the edges.

The background should remain visually simple.

---

## 5.3 Background effects

When paused:

- background is essentially static
- no obvious movement

When playing:

- introduce a very slow ambient breathing glow
- extremely low amplitude
- long animation duration
- low opacity

The effect should communicate that the radio is alive.

It should NOT look like a visualizer.

---

The overlay must protect readability.

Do not remove the core visual identity simply because a custom image is supplied.

# 9. Central Radio Card

The central display is the primary visual element.

## 9.1 Shape

Use:

- large rounded corners
- rectangular landscape shape
- thin border
- translucent interior
- glass-like appearance

Desktop target:

- approximately 730–760px wide
- approximately 350–370px high

Do not treat these values as rigid requirements. Preserve the visual proportions of the reference.

---

## 9.2 Surface

The card should use:

- translucent dark burgundy
- backdrop blur
- subtle internal glow
- subtle external glow
- thin warm border

The card must remain readable against the background.

---

## 9.3 Border

The border should be:

- thin
- warm cream/coral
- partially translucent
- slightly brighter than the card interior

Avoid thick borders.

---

## 9.4 Shadow/glow

Use a very soft glow.

The glow should become slightly more noticeable when music is playing.

It should never become a neon box.

The center of the card contains the current radio message.

Example:


Possible backend data:


Examples of different values:

```text

```

```text

```


# 14. Main Display Typography

Use a sophisticated serif font.

Potential font families:

- Cormorant Garamond
- Playfair Display
- DM Serif Display
- Libre Baskerville

The final choice should be based on which most closely matches the supplied reference.

Typography should be:

- light
- elegant
- warm ivory/cream
- centered
- generous
- non-bold

Do not use a heavy sans-serif for the primary romantic display.

---

# 15. Dynamic Text Transition

When the backend changes `displayText`, animate the change subtly.

Desired behavior:

```text
old text
   ↓
fade out + tiny movement
   ↓
new text
   ↓
fade in + tiny movement
```

Avoid:

- typing animations
- large scaling
- bouncing
- dramatic rotations
- flashy transitions

The change should feel like the radio is moving into its next moment.

CSS transitions are sufficient.

Framer Motion may be used if it makes the transition cleaner.

---

# 16. Waveform

The waveform beneath the main display must be generated by the frontend.

Do NOT use a waveform PNG.

Use:

- React-generated elements
- CSS
- optional Web Audio API

Conceptually:

```text
····▂▃▅▇▅▃▂····
```

The exact waveform should be visually similar to the reference.

---

# 17. Waveform — Paused State

When audio is paused:

- waveform remains visible
- bars are mostly static
- opacity is slightly reduced
- animation is disabled or nearly imperceptible

The radio should look calm.

---

# 18. Waveform — Playing State

When audio is playing:

- bars animate vertically
- animation speeds vary
- animation heights vary
- movement is smooth
- animation remains subtle

Do not make it a large nightclub-style equalizer.

The waveform should remain a small decorative element.

---

# 19. Optional Real Audio-Reactive Waveform

For a more advanced implementation, support the Web Audio API.

Architecture:

```text
HTML Audio
    ↓
AudioContext
    ↓
AnalyserNode
    ↓
Frequency Data
    ↓
Waveform Bars
```

This can allow the bars to respond to actual audio amplitude/frequency.

This is optional for V1.

Recommended progression:

### V1

Use CSS animation.

### V2

Use Web Audio API for actual audio-reactive movement.

# 28. Station Switching

Selecting a station should:

1. update selected station
2. close dropdown
3. request/select the appropriate current frame
4. update station display
5. update dynamic message
6. update audio source
7. preserve the overall radio experience

The UI should not reload the whole page.

---

# 29. Previous / Next Controls

The reference contains left and right circular arrow buttons beside the central card.

Both must be functional.

## Previous

Should select the previous available frame/item.

## Next

Should select the next available frame/item.

Use vector icons.

Do not use arrow images.

---

# 30. Navigation Button Appearance

Buttons should:

- be circular
- have thin warm borders
- have transparent/dark interiors
- glow slightly on hover
- have comfortable touch targets
- remain visually secondary to the play button

---

# 31. Audio Architecture

Use a real HTML `<audio>` element.

The frontend must not fake playback by simply changing React state.

Playback state should reflect actual audio state.

The player should manage:

- current audio URL
- playing
- paused
- loading
- error
- ended
- current frame
- duration

A reusable hook such as:

```text
useRadioPlayer
```

is recommended.

---

# 32. Continuous Frame Playback

The radio is intended to work with generated audio frames.

Conceptual flow:

```text
Frame 101
   ↓
audio ends
   ↓
Frame 102
   ↓
audio ends
   ↓
Frame 103
   ↓
audio ends
   ↓
Frame 104
```

The user should not need to manually press Play between frames.

Use the audio element's ended event.

---

# 33. Dynamic Backend Data

The frontend should be designed around dynamic data.

Possible frame structure:

```text

station
displayText
title
audioUrl

```

Do not hardcode these values in UI components.

# 34. API Service Layer

Do not put API requests directly throughout components.

Create a dedicated service layer.

Conceptual responsibilities:

```text
getCurrentFrame()
getNextFrame()
getPreviousFrame()
getQueue()
markFrameStarted()
markFramePlayed()
sendHeartbeat()
```

The exact API implementation can initially use mocks.

Later it should be replaceable with the real backend without rewriting the UI.

---

# 35. Mock Mode

The page must be runnable before the backend is complete.

Provide mock radio data.

The mock mode should allow:

- station rendering
- dynamic display text
- next/previous behavior
- station switching
- audio player state
- UI animations

If demo audio is unavailable, the interface should still render gracefully.

---

# 36. Music Playing State

Use a single authoritative state:

```text
isPlaying
```

This state should drive:

- waveform animation
- background breathing
- card glow
- play button glow
- decorative sparkle activity
- other subtle audio-related effects

Avoid maintaining duplicate `isPlaying` states across components.

---

# 37. Loading State

When a new frame/audio is loading:

Do not show a generic large spinner.

Use subtle feedback such as:

- reduced waveform
- tiny shimmer
- understated "tuning..." text
- gentle opacity transition

The radio interface should remain recognizable.

---

# 38. Error State

If audio fails, do not replace the entire page with an error screen.

Show a small radio-like status message.

Examples:

```text
signal lost
```

or:

```text
trying to reconnect...
```

Keep the controls and overall composition intact.

The exact text should be configurable.

---

# 39. Music-Reactive Ambient Effects

When music is playing, introduce subtle effects around the page.

## 39.1 Background breathing

Very slow radial glow.

## 39.2 Card glow

Slight increase in panel glow.

## 39.3 Play button glow

Slow breathing illumination.

## 39.4 Waveform

Animated bars.

## 39.5 Decorative lines

Optional very subtle shimmer.

## 39.6 Sparkles

Optional tiny brightness variation.

All effects should be extremely restrained.

---

# 40. Animation Rules

The animation language should be:

- slow
- soft
- smooth
- low amplitude
- opacity/transform based

Prefer:

- opacity
- transform
- filter
- box-shadow

Avoid continuously animating expensive layout properties.

---

# 41. Animation Timing

Suggested ranges:

## UI interactions

```text
150ms – 300ms
```

## Text transitions

```text
300ms – 600ms
```

## Background breathing

```text
4s – 8s
```

## Play button breathing

```text
3s – 5s
```

## Waveform

```text
0.5s – 1.2s
```

Use varied delays to avoid synchronized movement.

---

# 42. Hover States

Buttons should respond gently to hover.

Examples:

- slight brightness increase
- slight border brightness increase
- small glow increase
- very subtle scale increase

Avoid large transforms.

---

# 43. Click States

Buttons should have a tactile response.

Use:

- tiny scale reduction
- glow change
- fast transition

The interaction should feel physical but elegant.

Bootstrap is not required for the visual design.

- custom spacing
- custom borders
- gradients
- glass effects
- glow
- typography
- bespoke animation

Do not make the interface look like a Bootstrap template.

# 54. CSS vs Framer Motion

Recommended approach:

## CSS

Use CSS for:

- gradients
- borders
- glow
- waveform animation
- background breathing
- hover states
- button states
- decorative lines
- sparkles
- responsive styling

## Framer Motion

Use only where it improves:

- dynamic text transitions
- station dropdown transitions
- component entrance/exit
- more complex state transitions

Do not use Framer Motion for every animation.

# 56. Performance

The page should remain lightweight.

Avoid:

- unnecessary rendering
- huge image assets
- continuously expensive calculations
- dozens of DOM elements for decorative effects
- excessive blur layers
- unnecessary libraries

Keep the waveform reasonably small.

Use CSS animations wherever possible.

# 57. Custom Background Performance

- prefer WebP/JPG
- optimize file size
- use `background-size: cover`
- avoid giant uncompressed images
- apply a single overlay layer

Do not require a high-resolution photographic background for the default experience.

```text

→ audio starts
→ isPlaying becomes true
→ waveform animates
→ background breathes
→ card glows
→ button glows
```

## Pause

```text
User clicks Pause
→ audio pauses
→ isPlaying becomes false
→ effects calm down
```

## Audio ends

```text
Audio ends
→ next frame selected
→ display updates
→ next audio loads
→ playback continues
```

## Next

```text
Next clicked
→ next frame
→ dynamic display updates
→ audio updates
```

## Previous

```text
Previous clicked
→ previous frame
→ dynamic display updates
→ audio updates
```

```text
→ dropdown opens
```
